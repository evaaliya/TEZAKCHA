Кратко про sponsorship: сеть Solana берёт крошечную комиссию в **SOL**. Обычный кошелёк должен иметь SOL, иначе перевод не уйдёт. **Sponsorship** значит: приложение платит эту комиссию со своего служебного кошелька, а пользователь только подписывает перевод USDC — SOL ему для отправки не нужен.

Ниже — обновлённая расписка в формате **Must / Should / Out of scope**.

## Задание. TEZAKCHA

Продукт — банковский интерфейс для международных переводов. Сейчас основной коридор: **RUB ↔ KGS** (туда и обратно). Под капотом — детерминированный движок маршрутов и расчёт выбранного Solana-маршрута через USDC. В UI нет крипто-терминов: суммы, получатель, переплата относительно официального курса, срок доставки.

### Must

1. **Вход:** почта (и пароль / magic link / passkey — как решите в реализации). Создание встроенного кошелька без показа seed phrase. Подпись отправки — Phantom в десктопном браузере.
2. **Экран отправки:** сумма, валюта отправителя, валюта получателя, получатель (имя + контакты). На старте поддерживаются **RUB → KGS** и **KGS → RUB**. Валюты не зашиты в UI как «только рубль»: выбор из актуального набора коридора.
3. **Движок маршрутов:** чистая функция; деньги только через `Decimal`; округление вниз; одинаковый вход → одинаковый выход. Маршруты: традиционный перевод, банковский перевод, Solana+USDC с вариантами вывода. Сортировка по сумме к получению, при равенстве — по ETA.
4. **Экран сравнения:** несколько маршрутов, лучший выделен; сумма к получению, «дороже официального курса», разбивка комиссий, ETA, пометки оценок, источники курсов (НБКР / Банк России) и время обновления.
5. **Отправка Solana:** prepare → подпись Phantom → submit → confirm на **devnet**. Реальный SPL USDC transfer; Memo с `route_id` / `prepare_id`.
6. **Fee sponsorship:** сетевую комиссию в SOL платит приложение; пользователю не нужно держать SOL, чтобы перевод ушёл.
7. **Экран получателя** и **история** (статус, explorer-ссылка для судей).
8. **Локализация** ru / ky (en fallback); ошибки простым языком.
9. **Курсы:** mid с официальных источников с кэшем/откатом; фиатные on/off-ramp — оценка, всегда помечена. Расхождение котировки при prepare → `quote_changed`, без создания tx.
10. **Честность:** нет demo-подписей и фейковых «доставлено»; нет ключей/RPC → явная ошибка `solana_not_configured`.

### Should (если останется время)

- Разбор ELQR (О!Деньги) в телефон/сумму без открытия ссылки из QR.
- QR на получение (Solana Pay) / запрос на получение.
- Голосовое прочтение экрана подтверждения на кыргызском.
- Расширение набора валют сверх RUB/KGS в рамках той же модели коридоров (те же правила движка, новые fixtures/adapters).
- Идемпотентность prepare/submit, rate limit на send, строгая валидация суммы/телефона/адреса.
- **БД для истории переводов** (сейчас журнал в памяти процесса и сбрасывается при рестарте; on-chain tx остаются в explorer).

### Out of scope

- Реальные on/off-ramp (KYC, банки, платёжные провайдеры) — в демо только симуляция фиатных ног.
- Mainnet.
- LLM в расчёте курсов/маршрутов.
- Multichain, свопы, кастомные смарт-контракты (достаточно SPL transfer).
- Показ seed phrase / требование к пользователю держать SOL при включённом sponsorship.

### Ожидаемое поведение (коротко)

- Один вход в движок + один снимок курсов → один и тот же набор маршрутов.
- На сравнении видно, сколько получит получатель и насколько это дороже официального mid; лучший — max к получению.
- При подтверждении Solana-маршрута сервер пересчитывает; курс уехал — отказ `quote_changed`, без tx.
- До cosign проверяются баланс USDC, SOL у fee payer, получатель, целостность tx от кошелька; любое изменение → `tx_mismatch`.
- «Доставлено» только после confirm в сети и совпадения дельты USDC у получателя.
- Повтор с тем же `idempotency_key` не создаёт вторую транзакцию.
- В UI нет token / gas / seed / wallet address; суммы в выбранных фиатных валютах.
- Фиатные звенья и USDC→фиат на экране получателя помечены как оценка; devnet-USDC без рыночной стоимости.
- Невалидные сумма / контакты / QR отклоняются до расчёта/отправки.
- После рестарта сервера: курсы из кэша/fixtures; истекшие prepare → `expired`; для живых prepare — либо устойчивое хранение и продолжение submit, либо новый prepare (вариант зафиксировать в README).
